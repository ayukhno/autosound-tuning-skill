## Вибір шляху

### Чотири варіанти використання

* 🖥️ **Варіант 1 · Версія 3.x у графічному вікні (Autosound TCC) — [Рекомендовано]**  
  Найбільш автоматизований та наочний шлях. Інсталятор встановлює Claude Code, Python, ядро методу, графічну оболонку та автоматичного рецензента.
  * **Вимоги:** macOS або Windows, платна підписка Claude Pro/Max, бета-версія REW з увімкненим API; застосунок додає близько 700 МБ до завантаження.
  * **Плюси:** Ти бачиш дерево системи, криві замірів, покроковий план і вікно чату в одному інтерфейсі. Стан записується на диск автоматично, а дії в реєстрі версій фіксуються.
  * **Мінуси:** Графічний застосунок молодший за саме ядро методу і наразі має статус бета-версії.

* 💻 **Варіант 2 · Версія 3.x у Терміналі (Claude Code або плагін без GUI)**  
  Те саме сучасне ядро, розрахункові інструменти та рівень автоматизації, але взаємодія ведеться текстом у консолі. Встановлюється з прапорцем `--terminal` (або як плагін Claude Code).
  * **Вимоги:** Ті самі підписки та бета-версія REW з увімкненим API, але без графічної оболонки.
  * **Плюси:** Максимальна швидкість виконання, нульові витрати ресурсів на GUI, ідеально для поціновувачів консолі. Проєкти на 100% сумісні з графічним застосунком TCC.

* 🏆 **Варіант 3 · Лінійка 2.x (Перевірена на змаганнях)**  
  Класичний плагін для Claude Code, зафіксований на версії `v2.8.3` (гілка `2.x`). За цим алгоритмом налаштоване авто автора здобуло нагороди у 2026 році на чемпіонатах EMMA та AYA.
  * **Вимоги:** Платний Claude Pro, бета-версія REW з увімкненим API, робота в терміналі.
  * **Плюси:** Фіксований, перевірений змаганнями алгоритм. Отримує лише виправлення критичних помилок, без додавання нових функцій.
  * **Мінуси:** Ручне ведення стану у текстових файлах Markdown (`dsp-state-current.md`), відсутність автоматичного прогнозу за столом («Спочатку за столом») та сучасних розрахункових інструментів.

* 🌐 **Варіант 4 · Веб-чат (Без встановлення програм на ПК)**  
  Повністю ручний покроковий процес налаштування за інструкціями з гілки [manual_step-by-step](https://github.com/ayukhno/autosound-tuning-skill/tree/manual_step-by-step).
  * **Вимоги:** Безкоштовний Google AI Studio або будь-який веб-чат з обраним тобою ШІ.
  * **Плюси:** Повністю безкоштовно. Не вимагає встановлення програм чи інструментів розробника на комп'ютер.
  * **Мінуси:** Кожен крок виконується вручну (копіювання промптів, самостійний експорт текстових файлів з REW), немає інтеграції з API та перевірки розрахунків локальними скриптами.

### Який варіант мені обрати?

* **Хочеш максимум автоматизації та візуального зворотного зв'язку:** Обирай **Варіант 1 (TCC)**.
* **Віддаєш перевагу консолі та максимальній швидкості:** Обирай **Варіант 2 (3.x Термінал)**.
* **Потрібен класичний перевірений змаганнями плагін:** Обирай **Варіант 3 (2.8.3)**.
* **Хочеш протестувати логіку безкоштовно без локальних програм:** Обирай **Варіант 4 (Веб-чат)**.

> [!NOTE]
> Ти не прив'язаний до одного вибору: проєкти лінійки 3.x безперешкодно відкриваються як у консолі, так і в графічній програмі TCC.

### Як перевірити поточну встановлену версію?

* **За використаною командою:** Якщо ти встановлював плагін командою `/plugin install autosound-tuning` усередині Claude Code — у тебе версія **2.x**. Якщо запускав однорядковий скрипт встановлення (`curl … | bash` або `irm … | iex`) — у тебе версія **3.x**.
* **За вмістом папки проєкту:** Якщо в папці лежить файл `dsp-state-current.md` — це проєкт **2.x**. Якщо там машинні файли `project.json` та `process-state.json` — це проєкт **3.x**.
* **Через інтерфейс застосунку:** У програмі TCC перейди в меню *Diagnostics → Installation*.

---

### Як залишитися на стабільній лінійці 2.x?

Стандартне автоматичне оновлення плагіна не переведе тебе на версію 3.x без твоєї згоди. Проте, якщо ти хочеш повністю заморозити версію та локально контролювати оновлення на гілці 2.x, клонуй репозиторій самостійно:

```bash
git clone -b 2.x https://github.com/ayukhno/autosound-tuning-skill.git ~/autosound-2x
```

Потім виконай ці дві команди в терміналі:
```bash
claude plugin marketplace add ~/autosound-2x
claude plugin install autosound-tuning
```
Тепер твій плагін вказує на локальну папку. Оновлювати його можна за потреби простою командою `git -C ~/autosound-2x pull`.

### Перехід з 2.x на 3.x

У системі може бути активним лише один такий плагін. Перед встановленням версії 3.x обов'язково видали стару версію 2.x (у терміналі):

```
claude plugin uninstall autosound-tuning
claude plugin marketplace remove autosound-tuning-skill
```

Після встановлення версії 3.x ти можеш перенести стан наявного автомобіля в новий машинний формат за допомогою автоматичного мігратора:

```sh
python3 ~/.claude/skills/.autosound-tuning-src/skills/autosound-tuning/rew_tool/state/migrate.py <path-to-old-project> --into <path-to-new-project>
```
*(Примітка: після запуску міграції перевір відповідність каналів та характеристики динаміків).*

### Головні зміни в 3.x

* 📦 **Проєкт як структура даних:** Усі системні параметри зберігаються на диску в `project.json` та `process/process-state.json`. ШІ зчитує точні машинні факти з диска замість того, щоб покладатися на пам'ять чату.
* 🛋️ **Підхід «Спочатку за столом»:** Замість багатьох виїздів до авто — **одна дисциплінована сесія для акустичної зйомки** (Фаза 0) та **один короткий візит для перевірки** (Фаза 3). Увесь аналіз, розрахунки кросоверів, узгодження фази та проєктування EQ виконуються за столом.
* 🧮 **Математична верифікація:** Спеціальні локальні скрипти Python аналізують криві за критерієм мінімальної втрати фази, оцінюють початок прильоту імпульсу та перевіряють стабільність часу мікрофона.
* 🛑 **Структуровані шлюзи:** Якщо вхідні заміри показують надмірний часовий дрейф, пропущені канали або порушені межі безпеки, система зупиняється та називає проблему перед тим, як рухатися далі.

## Філософія та архітектура: навіщо тут ШІ?

### Місія та концепція

Ми створюємо **інтелектуальний екзоскелет** для налаштування звуку. Людина (Арбітр) завжди залишається ключовою ланкою — слухає систему, оцінює глибину, висоту та стабільність сцени й приймає остаточні рішення.

ШІ бере на себе рутинні розрахунки та акустику салону: аналізує прильоти імпульсів, криві фази, розраховує часові затримки на стиках кросоверів та взаємодіє з REW через API, звільняючи твій час для творчої частини прослуховування музики.

---

### Чому це спеціалізований скіл, а не звичайний чат?

* **Стан збережений на диску:** Звичайний чат ШІ забуває початкові значення, плутає рівні гучності або змінює частоти кросоверів протягом довгої сесії. Наша система записує стан проєкту на диск. ШІ читає цей файл на кожному кроці — його контекст спирається на стан на диску, а не на буфер пам'яті чату.
* **Спеціалізовані знання з автоакустики:** Скіл містить суворі правила захисту динаміків, логіку узгодження фази, готові цільові криві та евристики акустики салону, про які універсальні моделі ШІ нічого не знають.
* **Локальна обробка через REW API:** Сирі дані замірів (тисячі точок на кожну криву) обробляються локально скриптами Python за мілісекунди. ШІ отримує в чат лише стислий математичний підсумок, що заощаджує час і бюджет на токени.

### Карта налаштування: Фази −1…5 та підхід «Спочатку за столом»

| Фаза | Де відбувається | Що виконується | Результат етапу |
| :--- | :--- | :--- | :--- |
| **−1 Підготовка** | за столом | Введення базових налаштувань (канали динаміків, виходи DSP, профіль DSP, мікрофон, референсне сидіння). Близько 17 відповідей одразу; решту запитує та фаза, якій це потрібно. | Створено `project.json` та файли конфігурації. |
| **0 Зйомка** | в авто (1 раз) | Замір кожного динаміка з **увімкненими захисними фільтрами** (свіпи на штативі `(sw)` та усереднені `(rta)`). Фіналізація цільової кривої після зйомки. | Перевірений раунд базових замірів та активна цільова крива. |
| **1 Основа** | за столом | Ти описуєш побажання щодо кросоверів своїми словами, і їх перевіряють на жорсткі межі. ШІ пропонує щонайбільше три варіанти кросоверів — найкращий за математикою та побудовані з твоїх побажань, кожен зі своєю ціною, — і обираєш ти. Тут же резонанси динаміків і грубий EQ для кожного динаміка; рівні, полярності й затримки знімаються вручну з початку кожного імпульсу; суми прогнозуються й описуються. | Базове налаштування системи в реєстрі версій. |
| **2 Еквалайзер** | за столом | Друга частина EQ, **пакетами** і в такому порядку: пари лівий/правий на смугу → стики кожного борту → саб із мідбасами → кожен борт цілком → усе разом → центр → тил. За замовчуванням **лише зрізи (cuts only)**, не більше 6 смуг на канал. Кожен пакет — це одне рішення «так/ні» та нова версія в реєстрі. | Готова конфігурація EQ для імпорту в DSP. |
| **3 Вердикт** | в авто (коротко) | Завантаження параметрів у DSP. Контрольний свіп автоматично перевіряє, чи реальні заміри збігаються з математичними прогнозами. Обов'язкова оцінка на слух. | Повністю перевірене та зафіксоване технічне налаштування. |
| **4 Слухання** | в авто | Тестові треки (диски EMMA/AYA, CarMus, Chesky) та шпаргалка «що слухати». Якщо щось гуде або звучить різко, скіл формує список підозрілих смуг і тестує їх по одній в A/B (три підозрювані × три раунди, потім стоп). | Вердикти прослуховування, прив'язані до версій. |
| **5 Варіації** | за столом / в авто | Налаштування додаткових пресетів (під різні музичні жанри, інший характер звучання) поверх технічної бази. | Додаткові звукові пресети в DSP. |

### Що метод категорично відмовляється робити?

* **Записувати параметри напряму у твій DSP** — введення значень у софт процесора завжди залишається твоєю дією.
* **Рахувати затримки за автооцінками чи крос-кореляцією** — акустичні затримки перевіряються вручну за первинним підйомом імпульсного відгуку ($t_0$). Інструменти автооцінки затримки в REW суворо заборонені.
* **Підсилювати частоти в акустичних нулях (зонах взаємного гасіння)** — провали через інтерференцію спричинені відбиттями від меж салону, а не самим динаміком. Заповнювати їх еквалайзером марно: підйом лише навантажує підсилювач і динамік і нічого не змінює в точці прослуховування. Метод обмежує будь-який підйом стелею +6 дБ, а провал, що вимагав би більшого, майже напевно є інтерференційним нулем. Ділянки, безпечні для корекції, визначаються за допомогою аналізу надлишкової фази (*Excess phase*) у REW.
* **Продовжувати роботу з компрометованими замірами** — виявлений часовий дрейф між контрольними свіпами сесії або відсутні захисні фільтри будуть позначені проблемою перед тим, як рухатися далі.

### Які моделі ШІ офіційно підтримуються?

* 🧠 **Основна модель (Генератор):** **Claude Opus** (на рівні зусиль `xhigh`; `max` для складного узгодження фази).
* 👁️ **ШІ-Критик (Рецензент):** **Gemini Pro (High)** через Google Antigravity (`agy`) або прямий API-ключ.
* 🛠️ **Інші рецензенти:** Меню вибору в TCC також пропонує Codex (а з прапорцем `--with-omp` — й інші моделі) на роль рецензента. Генератором завжди лишається Claude.

*Станом на вересень 2026 року.* Назви моделей швидко змінюються. Якщо модель, зазначену тут, відхилено (наприклад, `agy` відповідає, що модель не підтримується у твоєму регіоні), обери іншу з `agy models`.

> [!IMPORTANT]
> **Не знижуй рівень зусиль Claude нижче `xhigh`.**  
> Слабші моделі чи нижчі рівні зусиль не повідомлятимуть про помилки — вони тихцем погоджуватимуться з некоректними даними, вигадуватимуть неможливі акустичні параметри або пропускатимуть фазове гасіння.

## Графічний застосунок Autosound TCC

### Що це і чи обов'язково ним користуватися?

Застосунок [TCC](https://github.com/ayukhno/autosound-tcc) дозволяє працювати у графічному вікні на macOS та Windows. Ти бачиш дерево системи, графіки REW, покроковий план та чат із ШІ на одному екрані. Застосунок необов'язковий — налаштувати авто можна повністю через термінал, оскільки всі дані проєкту зберігаються в стандартних машинних файлах на диску.

📘 [TCC in eight screens (EN)](https://github.com/ayukhno/autosound-tcc/blob/main/docs/guide/QUICK-GUIDE.md) · [The TCC window, panel by panel (EN)](https://github.com/ayukhno/autosound-tcc/blob/main/docs/guide/REFERENCE.md) · [The house curve in TCC (EN)](https://github.com/ayukhno/autosound-tcc/blob/main/docs/guide/HOUSE-CURVE.md)

### Робота на два вікна (Термінал + Графіка)

Застосунок і термінал звертаються до тих самих файлів проєкту. Ти можеш вести інтерактивну сесію в терміналі, тримаючи поруч відкритим TCC як візуальний монітор реального часу: він відображає дерево динаміків, накладання кривих та зміни в реєстрі версій одразу, як тільки вони відбуваються.

### Моделі ШІ в застосунку

Застосунок використовує твою підписку Claude (через Anthropic SDK) та акаунт Google через `agy` для ШІ-рецензента. Вибір моделей у TCC відображає рекомендовані комбінації. Альтернативні моделі через `omp` додаються лише за явного запиту (`--with-omp`).

### Оновлення та повідомлення про помилки

TCC перевіряє наявність оновлень скіла та застосунку. Про проблеми інтерфейсу повідомляй у [репозиторії GitHub TCC](https://github.com/ayukhno/autosound-tcc/issues), а про математику налаштування — у [репозиторії скіла](https://github.com/ayukhno/autosound-tuning-skill/issues).

## Автономний ШІ-Критик Gemini/Antigravity

Цикл подвійної перевірки (Генератор ↔ Критик Gemini) відловлює помилки, яких одна модель припускається і не бачить. Він працює автоматично у фоні через локальний скрипт — ручне копіювання не потрібне. Необов'язковим є лише цей *автоматичний канал*, а не сама друга думка: якщо канал не налаштовано, ти вставляєш пакет у чат іншого ШІ вручну. Повний пропуск рецензування — це найбільша втрата якості в усьому методі.

### Встановлення для macOS та Windows (Рекомендовано)

Офіційний інструмент **Antigravity CLI (`agy`)** не потребує API-ключа — ти авторизуєшся в браузері під своїм Google-акаунтом.

1. **Встановлення:** Інсталятор налаштовує його автоматично. Для ручного встановлення виконай:
   * *macOS:* `curl -fsSL https://antigravity.google/cli/install.sh | bash`
   * *Windows:* `irm https://antigravity.google/cli/install.ps1 | iex`
2. **Вхід:** Запусти команду `agy` у новому терміналі, авторизуйся в браузері через Google-акаунт, потім повернися до консолі та введи `/quit`.
3. **Вибір моделі рецензента** — варіанта за замовчуванням немає. Впиши ідентифікатор із `agy models` (ліва колонка; рівень Pro `-high`) у файл конфігурації рецензента, `~/.config/autosound/critic-env` (`%APPDATA%\autosound\critic-env` на Windows), як рядок на кшталт:
   ```env
   AUTOSOUND_CRITIC_MODEL=gemini-3.1-pro-high
   ```
   Застосунок виставляє її зі свого меню вибору. Якщо `agy` відповідає, що модель не підтримується у твоєму регіоні, обери інший ідентифікатор зі списку.
4. **Перевірка:**
   ```bash
   python3 ~/.claude/skills/autosound-tuning/scripts/autosound_ai.py doctor
   ```
   `doctor` назве модель, знайдені CLI та ключ, виконає один короткий тестовий виклик і виведе рішення для будь-якої знайденої проблеми.

---

### Резервний варіант: прямий API-ключ Gemini

Якщо `agy` тобі недоступний або його квоти вичерпано, можна використовувати безкоштовний API-ключ Gemini напряму. За наявності ключа рецензент звертається до API **спершу**, і до `agy` — лише якщо цей виклик не вдався.

1. Отримай безкоштовний API-ключ на **[aistudio.google.com/apikey](https://aistudio.google.com/apikey)** — актуальні ключі починаються на `AQ.`.
2. Збережи його один раз власною командою рецензента. Вона запитує ключ без відображення на екрані та зберігає його в Keychain macOS (на Windows — у сховищі, яке відкриває лише твій логін; в інших системах і коли сховище недоступне — у конфігураційному файлі рецензента з правами 600). Рядок ключа, вписаний у `critic-env` вручну, має перевагу над сховищем. Ніколи не зберігай ключ у папці проєкту, профілі оболонки чи змінних оточення: там його може прочитати будь-яка програма, а застосунок, запущений із Dock, його просто не побачить.
   ```bash
   python3 ~/.claude/skills/autosound-tuning/scripts/autosound_ai.py key set google
   # Windows: python3 "$HOME\.claude\skills\autosound-tuning\scripts\autosound_ai.py" key set google
   ```
   Ключ, уже експортований у `~/.zshrc` (або в оточенні користувача Windows), переноситься командою `… key move-shell`, яка спершу запитує підтвердження. Команда `… key status` показує, де саме знаходиться кожен ключ, ніколи не розкриваючи сам ключ.
3. Вкажи модель, яку цей ключ може викликати: `doctor` виводить власний список ключа (наприклад, `gemini-pro-latest`). Її ідентифікатори відрізняються від ідентифікаторів `agy`.

Локальний файл `.critic-env` у папці проєкту, що містить ключ і який міг би підхопити git, відхиляється. `doctor` ніколи не виводить сам ключ, лише його формат (`current` / `OLD`) та джерело походження.

> [!TIP]
> Якщо жоден канал не відповідає, рецензент відмовляє (код виходу 4): він перераховує причини, зберігає пакет перевірки в папку проєкту `process/reviews/` та копіює його в буфер обміну — встав його в будь-який чат із ШІ.

## Проведення замірів

### Вимірювання фази: XLR-мікрофони проти USB (UMIK-1/2)

* **XLR-мікрофони (Behringer ECM8000, Beyerdynamic MM1 тощо):** Підключаються через зовнішню звукову карту з **апаратним кабелем loopback** (вихід карти з'єднаний напряму з вільним входом). Це дає стабільний на апаратному рівні відлік часу прильоту з точністю до одного семпла (один семпл ≈ 10 мкс при 96 кГц).
* **USB-мікрофони (UMIK-1 / UMIK-2):** Підключаються напряму через USB. Вони мають окремі від звукової карти цифрові тактові генератори та не мають фізичного loopback, тому потребують акустичного референсу часу.
* **Передача аудіо:** Використовуй фізичний дріт (AUX 3.5 мм, пряме USB-аудіо або оптику). **Уникай Bluetooth для свіпів:** бездротове з'єднання додає пакетний джиттер та змінну затримку, що погіршує точність акустичного референсу часу.

### Чи можна виміряти фазу на UMIK-1?

**Так.** Використовуй **Acoustic Timing Reference** в REW. Перед відтворенням вимірювального свіпу REW подає короткий високочастотний «чірп» через вихід, який ти обираєш як часовий референс, і цей чірп слугує нульовою точкою для вимірюваного каналу.

Детальне налаштування REW для USB-мікрофонів дивись у відеокерівництві: [Measuring Speaker Phase in REW](https://www.youtube.com/watch?v=El-kwZ5_nnU).

> [!WARNING]
> **Проводь заміри з мікрофоном на штативі та обов'язково повторюй контрольний свіп наприкінці!**
> * **Температурний дрейф повітря в салоні:** Швидкість звуку змінюється з температурою в салоні. Зміна на кілька градусів зміщує час прильоту на десятки мікросекунд.
> * **Дрейф накопичується з кожним свіпом:** один динамік, виміряний 6 разів поспіль протягом 18 хвилин, змістився на один семпл (10 мкс, що еквівалентно зміщенню мікрофона на ~3,6 мм) — саме від запуску свіпів, а не просто від плину часу.
> * **Розміщення штатива:** Встановлюй мікрофон на рівні вух для **референсного сидіння**, зафіксованого в проєкті, орієнтуючись за фізичними мітками, і не рухай його до завершення блоку.
> * **Контрольний свіп:** Замір початкового каналу (`ctl1`) та його повтор наприкінці (`ctl3`) дозволяє перевірці назвати будь-який часовий дрейф до закриття раунду; перезнімати чи ні — вирішувати тобі.

### Правила іменування замірів у REW

Розрахункові інструменти знаходять заміри суворо за їхніми назвами в REW:

* `m-L_1 (sw)` — канал `m-L` (лівий СЧ), серія замірів `1`, свіп на штативі. Стан DSP може мати кілька серій; цей номер також не є номером версії в реєстрі.
* `m-L_1 (rta)` — замір RTA в русі (moving-mic) для того самого динаміка.
* `tw-L_1 (sw)`, `w-R_1 (sw)`, `sw_1 (sw)` — лівий твітер, правий мідбас, сабвуфер відповідно.
* `L_1 (rta)`, `ALL_1 (rta)` — сумарний RTA-замір усього лівого боку або всієї системи.
* `m-L p5_1 (sw)` — динамік у просторовій контрольній точці `p5` (також читається як `m-L_1 (sw) p5`).
* `m-L-ctl1_1 (sw)` та `m-L-ctl3_1 (sw)` — контроль часу: перший відкриває серію динаміка, другий закриває її; `ctl2` немає (якщо ввести в авто `m-L_1ctl` та `m-L_1rep`, вони означають те саме).
* `m-L_final (sw)` — верифікаційний замір після збереження фінальних параметрів.
* `w-L (imp)` — замір імпедансу динаміка; він не прив'язаний до стану DSP і не містить номера серії.
* Текст після позначення методу робить його **іншим заміром тієї самої серії**: `r-L_17 (sw) noXO` — це не `r-L_17 (sw)`.

Назви звіряються точно символ у символ. Назва, що не відповідає очікуваній на цьому кроці, спричинить запитання від ШІ до тебе, а не здогадки.

Повний процес вимірювань описано в [`references/phases/capture-session-sheet.md`](skills/autosound-tuning/references/phases/capture-session-sheet.md).

### Сесія зйомки: чому тільки захисні фільтри?

> [!IMPORTANT]
> **REW має залишатися відкритим протягом усього процесу:** скіл зчитує криві напряму з активного вікна REW через API, а не з експортованих на диск файлів.
>
> **Захисні фільтри під час зйомки ЛИШАЮТЬСЯ ВВІМКНЕНИМИ:** Фільтри високих частот (HPF) на вразливих твітерах та середньочастотниках мають залишатися активними в DSP для їхнього захисту під час вимірювальних свіпів.

* **Правило захисного фільтра:** Захисний HPF повинен бути **$\ge 1.1 \times Fs$ (рекомендовано до $1.5 \times Fs$), із крутизною зрізу $\ge 24$ дБ/окт** (LR4 або BW4). Якщо $Fs$ невідома, подивись значення в паспорті виробника та вкажи його в проєкті.
* **Робочі фільтри вимкнені:** Робочий EQ (порожній), затримки (встановлені в 0) та полярності (нормальні) мають бути чистими. Зафіксуй кожен захисний фільтр у раунді зйомки (застосунок запитує; у терміналі це фіксує сесія): інструменти математично віднімуть його з цього соло-заміру перед розрахунком спільної фази. Канал, записаний як `OFF`, зчитується як є.
* **Рівні в dBFS:** Встановлюй гучність свіпу так, щоб пік найгучнішого динаміка (сабвуфера) був у межах $-5\dots-10$ dBFS, а найтихіший динамік звучав упевнено вище фонового шуму салону. Перевір рівень шуму як із заглушеним, так і з увімкненим двигуном. Заглуши (mute) усі неактивні канали в софті DSP і не змінюй гучність звукової карти та головного пристрою протягом усієї сесії.
* **Звук мідбаса під час свіпу:** Мідбас, виміряний без фільтра LPF, на високих частотах свіпу видаватиме різкий, деренчливий звук. Це нормальний **злам дифузора (cone breakup)** на верхній межі його діапазону; динамік не пошкоджено.

### Навіщо потрібні точки p1…p9 та контрольний замір ctl?

* **Як відрізнити резонанси динаміка та його кріплення від відбиттів салону:** Справжні резонанси залишаються стабільними при невеликому зміщенні мікрофона (їх безпечно коригувати еквалайзером). Салонні інтерференційні нулі сильно зміщуються за частотою — підсилювати їх марно.
* **Розрахунок меж добротності EQ:** Просторова дисперсія між точками `p1…p9` визначає безпечні межі добротності (Q) фільтрів еквалайзера.
* **Контроль часового дрейфу:** Початковий та кінцевий свіпи `ctl` виявляють дрейф тактових генераторів або температури протягом сесії.

## Цільові криві

### Як створити та налаштувати власну цільову криву?

Цільова крива — це початкова тональна гіпотеза, яку ти уточнюєш на слух після отримання базового технічного налаштування.

1. **Вибір із перевірених кривих:** Обери калібровану ціль — власну SQ-Comp-Ref методу, ResoNix, Audiofrog, Harman, Jazzi чи Whitledge — за тим, що тобі подобається чути. Скрипт `target_bands.py` розрахує індивідуальні форми цілей для кожного динаміка на основі обраної кривої та точок кросоверів.
2. **Малювання вручну:** Скористайся безкоштовним сервісом [Nono Tuning Tool](https://nonotuningtool.com) (розділ *Custom Target Curve*), щоб намалювати відгук та експортувати файл кривої `.txt`.
3. **Порівняння онлайн:** Відкрий наш інтерактивний онлайн-візуалізатор:  
   👉 **[Відкрити візуалізатор цільових кривих](https://ayukhno.github.io/autosound-tuning-skill/_curve-visualizer.html?lang=uk)**. Клік правою кнопкою миші на будь-якій точці графіка показує підказку про те, як цей частотний діапазон впливає на звук.

📘 [The house curve in TCC (EN)](https://github.com/ayukhno/autosound-tcc/blob/main/docs/guide/HOUSE-CURVE.md)

## Проєкт на диску та DSP

### Структура папки проєкту та резервне копіювання

Папка проєкту містить повну конфігурацію та історію налаштування автомобіля:

| Файл / Папка | Вміст | Призначення |
| :--- | :--- | :--- |
| **`project.json`** | Конфігурація системи | Канали динаміків, виходи DSP, профіль, характеристики мікрофона, цільова крива. |
| **`state/versions/` + `slots.json`** | Реєстр версій | Хронологічна історія кросоверів, затримок, рівнів та EQ. |
| **`process/process-state.json`** | Стан процесу | Відстеження активної фази та журнал верифікації. |
| **`autosound_context.md`** | Контекст авто | Словник автозвуку, особливості інсталяції, примітки щодо салону. |
| **`*.txt` / `*.json`** | Криві та експорт для DSP | Цільові криві та згенеровані файли параметрів EQ. |

> [!IMPORTANT]
> **Обов'язково зберігай локальні копії `.mdat`:** Метод вимагає зберігати локальну копію файлів замірів REW `.mdat` під час технічної фіксації та наприкінці сесії. Великі файли `.mdat` (від 16 до 112 МБ кожен) не потрапляють у git; твої локальні копії завжди мають залишатися збереженими. Для безкоштовного приватного бекапу папки проєкту на GitHub встанови інструмент із прапорцем `--github` (`-GitHub` на Windows) і попроси ШІ зробити бекап проєкту: він запропонує створити репозиторій, нічого не створить без твоєї згоди та знає, які саме файли не слід завантажувати.

### Сумісність із процесорами та імпорт фільтрів у DSP

> ⚠️ **Важливо:**  
> Метод розраховує фільтри. Затримки та гейни тюнер завжди виставляє **вручну**, як і кросовери, — хіба що їх підхопить інструмент вставки з експорту Extended нижче. Імпорт файлу переносить лише **EQ**.

* **Audiotec Fischer (Helix / MATCH / BRAX):** Формує готовий до імпорту файл Full EQ, який софт DSP PC-Tool завантажує одразу для всіх каналів в один крок.
* **Інші процесори DSP:** Експортує файли формату REW Generic EQ (20 слотів) або Generic/Extended із зазначенням кросоверів. Для швидкого введення параметрів в інший софт DSP за допомогою макросів клавіатури використовуй безкоштовну утиліту [REW-EQ-CopyPaste-Assistant](https://github.com/IvanBakhmutov/REW-EQ-CopyPaste-Assistant).
* **Перевірка сумісності:** Перед експортом скрипти порівнюють кожен розрахований фільтр з обмеженнями твоєї моделі DSP (доступні смуги, частота дискретизації, типи фільтрів) та попереджають про будь-які відхилення.
* **Штатні магнітоли (OEM):** Рекомендований підхід полягає в тому, щоб **обійти** штатну магнітолу за допомогою чистого прямого цифрового або аналогового входу (DAP, USB, оптика) у DSP, а не намагатися дееквалізувати заводські налаштування тону й тонкомпенсації.

### Робота з пасивними кросоверами (твітер + СЧ на одному каналі)

Пара динаміків на спільному пасивному кросовері розглядається системою як **один спільний канал DSP**: вона отримує один замір, спільну затримку, спільний гейн та один набір фільтрів EQ.

Усе інше працює як зазвичай, і сумарний відгук є фізично коректним — включно з будь-якими проблемами фази на стику пасивного кросовера. Чого жоден софт не може зробити ззовні — це вирівняти час або фазу між твітером і середньочастотником **всередині** цієї пасивної групи: для цього кожен динамік повинен мати власний канал DSP.
